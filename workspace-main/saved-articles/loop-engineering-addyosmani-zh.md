# 循环工程（Loop Engineering）

> 原文：[Addy Osmani](https://addyosmani.com/blog/loop-engineering/)
> 翻译日期：2026-06-16

循环工程，就是用你去设计系统来给 Agent 下提示，来代替你本人亲自给 Agent 下提示。这里的"循环"可以理解为一个递归目标——你定义一个目的，然后 AI 不断迭代直到完成。我认为这可能是我们使用编码 Agent 的未来方向。不过，这还处在早期阶段，我持怀疑态度，而且你必须对 Token 成本保持[警惕](https://x.com/weswinder/status/2063700289710964906)（Token 富足和匮乏的用法可能天差地别），所以我打算拆解一下它是什么、意味着什么。

Peter Steinberger 最近[说](https://x.com/steipete/status/2063697162748260627)："你不再应该亲自给编码 Agent 下提示了。你应该设计循环来给你的 Agent 下提示。"类似地，Anthropic 的 Claude Code 负责人 Boris Cherny 也[说](https://x.com/rohanpaul_ai/status/2063289804708835412)："我不再亲自提示 Claude 了。我有一些循环在运行，它们来提示 Claude 并决定做什么。我的工作是写这些循环。"

好吧，那这到底是什么意思？

过去两年里，你想从编码 Agent 那里拿到东西的方式是：写一个好的提示，提供足够的上下文。你输入一句话，读一下返回的结果，再输入下一句。Agent 是一个工具，你全程握着它，一轮接着一轮。这个时代差不多结束了——至少有些人认为是这样。

现在你构建一个小系统，它自己找任务、分发任务、检查结果、记录已完成事项、再决定下一步做什么。你让这个系统代替你去"戳"那些 Agent。我之前写过它的近亲——[Agent Harness 工程](https://addyosmani.com/blog/agent-harness-engineering/)，那是构建单个 Agent 运行的环境；还有[工厂模型](https://addyosmani.com/blog/factory-model/)——构建软件的系统。循环工程站在 Harness 的上层：Harness 放在定时器上跑，它会生成小帮手，自己喂自己。

让我惊讶的是，这已经不再是一个工具问题了。一年前，如果你想要一个循环，你得写一堆 bash 脚本，然后永远维护它，而且它是你一个人的。现在这些部件直接内置于产品中。Steinberger 的列表几乎完全对应到 Codex 应用上，然后也几乎一样对应到 Claude Code 上。一旦你注意到它们的结构相同，你就不再争论哪个工具更好，你只是设计一个循环，不管你在哪个工具里它都能跑。

## 五个部件，再加上笔记

一个[循环](https://x.com/reach_vb/status/2063713960495558940)需要五样东西，再加一个记住状态的地方。我先列出来，再对应到工具。

- **自动化（Automations）**：定时触发的自动化任务，自己完成发现和分类。
- **工作树（Worktrees）**：让两个并行的 Agent 不会互相踩到文件。
- **技能（Skills）**：把项目知识写下来，省得 Agent 每次都靠猜。
- **插件与连接器（Plugins & Connectors）**：把 Agent 接入你已经在用的工具。
- **子 Agent（Sub-agents）**：一个负责出点子，另一个负责检查。

然后是第六样——**记忆（Memory）**。一个 Markdown 文件或者一个 Linear 看板，任何存在于单次对话之外、记录已完成和待办事项的东西。听起来蠢到不值一提。但这是每个长期运行的 Agent 都依赖的同一个技巧——我在[长期运行 Agent](https://addyosmani.com/blog/long-running-agents/) 中深入讲过——模型会在运行之间忘记一切，所以记忆必须存在磁盘上，而不是上下文里。Agent 会忘记，但仓库不会。

现在两个产品都有了这全部五样。

| 原语 | 循环中的职责 | Codex 应用 | Claude Code |
|---|---|---|---|
| 自动化 | 按计划进行发现和分类 | [Automations 标签页](https://developers.openai.com/codex/app/automations)：选择项目、提示、节奏、环境；结果进入 Triage 收件箱；/goal 跑至完成 | 定时任务和 cron，/loop，/goal，钩子，GitHub Actions |
| 工作树 | 隔离并行功能 | 每个线程内置工作树 | git worktree，--worktree，子 Agent 上的 isolation: worktree |
| 技能 | 将项目知识编码 | [Agent Skills](https://developers.openai.com/codex/skills)（SKILL.md），通过 $name 或隐式调用 | [Agent Skills](https://addyosmani.com/blog/agent-skills/)（SKILL.md） |
| 插件/连接器 | 连接你的工具 | 连接器（MCP）加插件用于分发 | MCP 服务器加插件 |
| 子 Agent | 构思与验证 | [子 Agent](https://developers.openai.com/codex/subagents) 在 .codex/agents/ 中用 TOML 定义 | .claude/agents/ 中的任务子 Agent，Agent 团队 |
| 状态 | 跟踪已完成事项 | 通过连接器接入 Markdown 或 Linear | Markdown（AGENTS.md、进度文件）或通过 MCP 接入 Linear |

名称略有不同，但核心能力是一样的。我逐一展开，因为老实说，细节决定了循环是稳固可靠，还是悄无声息地到处漏水。

## 自动化——这是心跳

自动化才是让循环成为真正"循环"的东西，而不是你只跑一次的一次性任务。在 Codex 应用中，你在 Automations 标签页创建一个自动化，选择项目、要运行的提示、频率，以及运行在你的本地检出还是后台工作树上。找到东西的运行会进入 Triage 收件箱；什么都没找到的运行会自动归档——这很贴心。OpenAI 内部用它们来处理琐事：每日问题分类、汇总 CI 失败、编写提交简报、排查上周谁引入的 Bug。自动化还可以调用技能，所以你可以让重复性任务保持可维护性——你调用 `$skill-name` 而不是把一堵巨大的指令墙粘贴进一个永远不会被更新的调度计划里。

Claude Code 通过调度和钩子实现了同样的效果。你可以用 `/loop` 按间隔运行提示或命令，可以调度 cron 任务，可以在 Agent 生命周期的特定点用钩子触发 shell 命令，或者如果想在合上笔记本后继续运行，就把整个东西推到 GitHub Actions。完全相同的思路：你定义一个自主任务，给它一个节奏，发现的结果来找你，而不是你到处去检查。

还有一个值得了解的在会话内的原语，它更接近本文的核心。`/loop` 按节奏重复运行。`/goal` 持续运行直到你写的某个条件真正满足，每一轮之后有一个独立的小模型检查是否完成——这样写代码的 Agent 就不会给自己打分。你可以给它类似"test/auth 里的所有测试通过且 lint 干净"这样的条件，然后走开。Codex 也有同样的功能，同样叫 `/goal`，它跨轮次持续工作，直到一个可验证的停止条件成立，支持暂停、恢复和清除。同样的原语，两个工具都有——这也是本文的一个贯穿模式。

所以这是暴露工作的部分。循环的其余部分则是对这些工作采取行动。

## 工作树——防止并行变成混乱

一旦你运行超过一个 Agent，文件就会开始冲突，这就是失败的开端。两个 Agent 写同一个文件，和两个工程师没沟通就提交到同一行代码是同一个头痛。git worktree 解决了这个问题：它是一个独立的工作目录，在自己的分支上，共享同一个仓库历史，所以一个 Agent 的编辑碰不到另一个的检出。

Codex 内置了工作树支持，因此多个线程可以同时操作同一个仓库而不会互相冲撞。Claude Code 通过 git worktree 提供同样的隔离——`--worktree` 标志可以在自己的检出中打开一个会话，还有 `isolation: worktree` 设置可以附加在子 Agent 上，这样每个帮手都能获得一个干净且能自动清理的检出。我在[编排税](https://addyosmani.com/blog/orchestration-tax/)中写过所有这些人性化方面——工作树消除了机械层面的冲突，但**你**仍然是天花板，你的审查带宽决定了你实际能跑多少个 Agent，而不是工具本身。

## 技能——让你不再每次都重新解释项目

技能，就是让你不再像金鱼一样每个会话都重新解释同样的项目上下文。两个工具使用相同的格式：一个文件夹内含一个 SKILL.md，里面是指令和元数据，以及可选的脚本、参考资料、资源文件。Codex 在你用 `$` 或 `/skills` 调用技能时执行它，或者当你的任务匹配技能描述时自动执行——这也是为什么一个紧凑枯燥的描述优于一个花哨的描述。Claude Code 用同样的方式，我在 [Agent Skills](https://addyosmani.com/blog/agent-skills/) 中整理了这个模式。

技能也是让你的"意图"不再反复消耗成本的地方。我在[意图债务](https://addyosmani.com/blog/intent-debt/)中论证过，Agent 每次会话都是冷启动，它会用自信的猜测来填补你意图中的任何空洞。技能就是写在外部的那份意图——约定、构建步骤、"因为某次事故我们不这么干"——写一次，Agent 每次运行都会读到。没有技能，循环每次都要从零推导你的整个项目；有了技能，它就会不断累积。

有一点要搞清楚：技能是编写格式，插件是发布方式。当你想要跨仓库共享技能或把几个技能打包在一起时，你把它们打包成插件。在 Codex 中是这样，在 Claude Code 中也是这样。

## 插件与连接器——循环触及你的真实工具

一个只能看到文件系统的循环是一个很小的循环。连接器基于 MCP 构建，让 Agent 能够读取你的问题跟踪器、查询数据库、访问预发 API、在 Slack 中发消息。Codex 和 Claude Code 都支持 MCP，所以你为一个工具编写的连接器通常可以在另一个中直接使用。插件将连接器和技能打包在一起，让你的队友一次安装好你的整个配置，而不需要凭记忆重建一切。

这就是说"这是修复方案"的 Agent 和能自动提交 PR、关联 Linear 工单、CI 通过后自己 Ping 频道的循环之间的区别。连接器是循环能在你的**实际环境**中行动、而不只是告诉你会做什么的原因。

## 子 Agent——让"制造者"远离"检查者"

循环中最有用的结构，远远超过其他，就是把写代码的人和检查代码的人分开。写代码的模型给自己打分时太宽容了。第二个 Agent——使用不同的指令，有时使用不同的模型——能抓住第一个自己说服自己通过的问题。

Codex 只在你要求时生成子 Agent，同时运行它们，然后将结果合并到一个答案中。你在 `.codex/agents/` 中用 TOML 文件定义你自己的 Agent，每个都有名称、描述、指令以及可选的模型和推理力度——所以你的安全审查员可以用一个强力模型配合高推理力度，而你的探索者可以是一个快速的只读 Agent。Claude Code 同样用 `.claude/agents/` 中的子 Agent 和在它们之间传递工作的 Agent 团队来实现同样的功能。两者常见的分工是：一个 Agent 探索，一个实现，一个对照需求验证。

我已经提过这个观点两次了：一次在[代码 Agent 管弦乐队](https://addyosmani.com/blog/code-agent-orchestra/)，一次在[对抗性代码审查](https://addyosmani.com/blog/adversarial-code-review/)。它在循环中特别重要的原因是：循环运行时你不在看，所以一个你真正信任的验证者是你敢走开的唯一理由。子 Agent 确实消耗更多 Token，因为每个都做自己的模型和工具工作，所以要把它们用在你认为第二意见值得付费的地方。这也基本上是 Claude Code 的 `/goal` 在底层做的事：一个全新的模型来判断循环是否完成，而不是做工作的那个——制造者和检查者的分离应用到了停止条件本身。

## 一个循环长什么样

把所有这些拼起来，一个线程就变成了一个小小的控制面板。这是我一直在用的一种形态。

每天早晨有一个自动化在仓库上运行。它的提示调用一个分类技能，读取昨天的 CI 失败、未解决的问题、最近的提交，然后把发现写入一个 Markdown 文件或 Linear 看板。对于每个值得处理的发现，线程打开一个隔离的工作树，派一个子 Agent 起草修复方案，再用第二个子 Agent 对照项目技能和现有测试审查该草案。

连接器让循环可以自动打开 PR 和更新工单。任何循环无法处理的内容落到我的 Triage 收件箱。状态文件是整个东西的脊梁，它记住了什么尝试过了、什么通过了、什么仍然未处理，这样明天早上运行时能接着今天停下的地方继续。

看看你实际上做了什么：你设计了一次。你没有手动下任何一步的提示。这就是 Steinberger 观点的真实体现——而且在 Codex 中或在 Claude Code 中是同样的循环，因为部件是相同的部件。

## 循环仍然不能为你做什么

循环改变了工作方式，但它没有把你从工作中删除。而且随着循环变得更好，三个问题实际上变得更尖锐，而不是更轻松。

**验证的责任仍然在你身上。** 无人值守的循环，也就是在无人值守时也在犯错的循环。你把验证子 Agent 和制造子 Agent 分开的全部原因，就是为了让循环说"完成了"时有点意义——但即便如此，"完成"也只是个声称，而不是证明。我一直在重复[AI 时代的代码审查](https://addyosmani.com/blog/code-review-ai/)中的同一句话：你的工作是交付你确认能工作的代码。

**如果你允许，你的理解力仍然会退化。** 循环交付你没写过的代码越快，存在的东西和你真正理解的东西之间的鸿沟就越大。这就是[理解力债务](https://addyosmani.com/blog/comprehension-debt/)——一个顺滑的循环只会让它增长得更快，除非你阅读循环交付的东西。

**最舒适的姿势，也是最危险的。** 当循环自我运行时，你很容易停止有自己的判断，只是接受它交回的任何东西。我称之为[认知投降](https://addyosmani.com/blog/cognitive-surrender/)。设计循环本身是解药——当你带着判断力去做的时候；也可以是催化剂——当你用它来逃避思考的时候。同一个动作，相反的结果。

## 构建循环，但保持工程师本色

我认为这是我们工作方式演进的预演。话虽如此，如果我不亲自审查代码，或者完全依赖自动化循环来修复问题，我产品的质量就会受损。我可能会陷入一个下降螺旋，不断把自己挖进一个更深的坑里。

所以，去设置你的循环吧，但不要忘记直接给 Agent 下提示也同样有效。关键在于找到正确的平衡。

循环的结果也会因你而异。两个人构建完全相同的循环，可能得到截然相反的结果。一个人用它来在自己深刻理解的工作上加速前进；另一个人用它来避免理解工作本身。循环不知道其中的区别。你知道。

这就是为什么循环设计比提示工程更难，而不是更简单。Cherny 的观点不是工作变容易了，而是杠杆点移动了。

构建循环。但要像一个打算保持工程师本色的人那样去构建——而不只是一个按下"运行"按钮的人。
